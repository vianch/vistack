# token-guard

An agent that opens a file over 5,000 tokens spends a large share of its working context on
that one file, and a reviewer cannot hold the file in their head. A pre-commit hook blocks a
staged file over the limit, the same check runs on the files a change under review touches,
and every block carries a split plan read from the file itself.

Tokens are `ceil(bytes / 4)`, counted on bytes rather than characters. The estimate needs no
tokenizer, so the hook runs anywhere Node 18 runs.

## Commands

`skills/token-guard/scripts/token-guard.mjs` runs the check and imports the split plan from
`skills/token-guard/scripts/split-plan.mjs` by a relative path; neither imports anything outside
Node. The script path resolves from the plugin root while the working directory stays in the
consuming repository.

| Host | Invocation |
|---|---|
| Claude Code | `node "${CLAUDE_PLUGIN_ROOT}/skills/token-guard/scripts/token-guard.mjs" <command> [flags]` |
| Codex | the same command with the installed plugin path in place of `${CLAUDE_PLUGIN_ROOT}` |

| Command | What it does |
|---|---|
| `check` (the default) | measures the index copy of every staged file and reports each one over the limit |
| `check --files <path>...` | measures those worktree files instead; works outside a repository, where `.gitattributes` is not read |
| `check --json` | prints `{ limit, checked, skipped: [{ path, reason }], over: [{ path, bytes, tokens, over, kind, suggestions }] }` on stdout |
| `explain <path>` | prints the split plan for one worktree file, whatever its size |
| `install [--limit <n>]` | writes the pre-commit hook in the consuming repository (see Install) |
| `uninstall` | removes the hook block and both copied scripts; a second run finds nothing and says so |

The limit is `--limit <n>`, else `TOKEN_GUARD_LIMIT`, else 5000. A file at exactly the limit
passes, and a pass prints nothing. Raise the limit only after the team agrees, because every
file then grows toward the new number.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | nothing over the limit, or install, uninstall, or explain done |
| `1` | an unknown command or flag, a limit that is not a positive whole number, or a missing path |
| `2` | at least one file over the limit; the message goes to stderr and `--json` output to stdout |
| `3` | git is not installed, or the command needs a repository and the working directory is outside one |

## What is ignored

The check skips only files no agent authors. Splitting lock data, build output, binaries, or
generated code helps no reader, and a limit that fires on them teaches people to bypass it.
The rules run in this order, and the first match names the `reason` in `skipped`:

| Rule | `reason` |
|---|---|
| index mode 120000 or 160000, or a directory passed to `--files` | `symlink`, `submodule`, `directory` |
| a lockfile by name (`lockfiles` in the script) or any `*.lock` | `lockfile` |
| a directory named `node_modules`, `vendor`, `dist`, `build`, `.next`, `coverage`, `__generated__`, `generated`, or `__snapshots__`; a name matching `*.generated.*`, `*.gen.*`, `*.pb.go`, `*_pb2.py`, `*_pb2_grpc.py`, `*.pb.ts`, `*.min.js`, `*.min.css`, `*.map`, or `*.snap` | `generated path` |
| an image, font, audio, video, archive, or native binary extension (`binaryExtensions` in the script) | `binary extension` |
| a NUL byte in the first 8,000 bytes | `binary content` |
| `@generated`, `DO NOT EDIT`, `AUTO-GENERATED`, `Code generated by`, or `automatically generated` in the first 10 lines, any case | `generated header` |
| `.gitattributes`: `linguist-generated` set or `true`, `token-guard=ignore`, or `-token-guard` | `linguist-generated`, `token-guard=ignore`, `-token-guard` |

The `.gitattributes` lookup runs only for files over the limit, so a small marked file counts
as checked.

## The split plan

| `kind` | The plan names |
|---|---|
| `TypeScript/React`, `JavaScript/React`, `TypeScript`, `JavaScript` | exported declarations (one component per file), types for `types/<area>.d.ts`, non-exported helpers, PascalCase and SCREAMING_CASE literal constants |
| `TypeScript tests`, `JavaScript tests` | top-level `describe` blocks by size, one file per describe |
| `Python` | top-level `def` and `class` by size, and a package whose `__init__.py` re-exports them |
| `Markdown` | H2 sections by size, the largest moved to `references/`; a `SKILL.md` over 500 lines is called out |
| `JSON`, `YAML` | top-level keys by size, one file per key, or the `.gitattributes` mark for data |
| `Other` | the line count and a split by responsibility |

## Install

A git hook runs outside Claude Code and Codex. `${CLAUDE_PLUGIN_ROOT}` is unset there, and a
tracked hook such as `.husky/pre-commit` must not carry a path that exists on one machine only.
So `install` copies `token-guard.mjs` and `split-plan.mjs` next to the hook it writes and calls
them by relative paths, which is why both import nothing outside Node. Run it in the consuming
repository.

| The repository has | `install` |
|---|---|
| `.husky/` | copies both scripts into `.husky/` and creates `.husky/pre-commit` or appends the block to it; commit all three files |
| `lefthook.yml` or `.pre-commit-config.yaml`, and no `.husky/` | writes nothing; prints the entry to add and the command that writes both copies to `scripts/` |
| neither | copies both scripts into the hooks directory (`git rev-parse --git-path hooks`, `.git/hooks` unless `core.hooksPath` is set) and creates or appends `pre-commit`, mode 0755 |

The block names only `token-guard.mjs`, which loads `split-plan.mjs` itself; ` --limit <n>` is
appended when `--limit` was given:

```sh
# >>> token-guard (keeps staged files under the token limit; remove this block to uninstall)
node "$(dirname "$0")/token-guard.mjs" check
# <<< token-guard
```

A second `install` with the block present changes nothing; a different `--limit` rewrites the
block. Each copy is one generated first line followed by the plugin's script, and `install`
rewrites a copy only when it differs from that, so a plugin upgrade reaches a repository only
when someone runs the plugin's `install` there again; run from a copy, `install` refreshes the
copies from themselves. `uninstall` removes the block and both copies from
whichever location holds them, and deletes a hook left holding only its shebang.

## In review

Run `check --files` on the paths from `git diff --name-only --diff-filter=ACMR <base>...HEAD`.
A file the change pushes over the limit is a finding that carries the printed split, posted as
`skills/review-pr/SKILL.md` describes.

## In a run

`install` can write tracked files in the consuming repository (`.husky/pre-commit`,
`.husky/token-guard.mjs`, and `.husky/split-plan.mjs`), so inside a viStack run it is a slice owned by the tier owner
(`skills/coordinate/SKILL.md`, Dispatch rules). `implementer` runs `check --files` on its
slice's files before committing.

## Gotchas

- This plugin's own `hooks/register.tsx` is 87,610 bytes (21,903 tokens) and
  `hooks/lib/monitors.ts` is 32,299 bytes (8,075 tokens). Both grew past the limit in small
  edits before any check existed. The hook catches a file only when it is staged, so a file
  already over the limit stays over until someone touches it, and that person's commit is the
  one blocked. After installing, run `check --files` on the largest files to see what the next
  edit will hit.
- The first husky install blocked its own commit. The copied `.husky/token-guard.mjs` was
  staged with the hook, and at 8,588 tokens it tripped the check. Both copies,
  `token-guard.mjs` and `split-plan.mjs`, now start with
  `// @generated by token-guard install; do not edit, run install again to update`, so the
  header rule skips committed copies, while the plugin's own sources carry no such line and are
  measured like any authored file. A test stages both copies and expects `generated header`.
